## Committing to Git with StrictDoc

We have started working on the Git Workspace feature, which allows users to commit changes to Git directly from the UI: [https://github.com/strictdoc-project/strictdoc/pull/3103](https://github.com/strictdoc-project/strictdoc/pull/3103).

The current conflict resolution UI works like this:

* Left column: the user's branch with the conflicting changes.
* Right column: the target branch, for example `main`.

Conflicts are shown at the traceability graph level rather than as line-by-line Git diffs.

### Challenge 1: Rebasing repeated conflicts

**The main challenge is preserving the user's commit history without making conflict resolution painful.**

For example, imagine that a user has made 20 commits while `main` has also changed significantly. With a normal Git rebase, Git replays those 20 commits one by one on top of the current `main`. If the same underlying change conflicts with `main` across several commits, the user may have to resolve essentially the same conflict again and again, potentially up to 20 times.

This is especially problematic for StrictDoc because conflict resolution happens through the traceability graph UI, where we want the user to resolve the logical conflict once rather than repeatedly resolve variations of it for every historical commit.

Our current workaround is to squash all user commits into a single commit before resolving conflicts. StrictDoc then compares the combined result of the user's work with the current target branch. The user resolves each conflict once, and StrictDoc creates one conflict-free commit on top of the target branch.

The obvious downside is that the original commit history is lost.

We are looking for feedback on whether there is a better Git workflow or algorithm that would allow us to resolve the combined conflict once while still preserving, or reconstructing, the user's original commit history.

**Possible solution**:

`rerere` could be used for applying the same conflict resolution patches repeatedly.

### Challenge 2: Resolve Git conflicts with non-doc changes

For example, a commit has changes to both documentation and code, e.g., Python
or TOML files.

Easy solution: Disallow resolving such conflicts, assuming that a user who
changes code will be able to resolve their conflicts with Git GUI or command-line.
